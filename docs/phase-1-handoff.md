## Safety boundaries

- Square Production access is read-only. Do not enable catalog, inventory,
  order, or payment mutations without a separate reviewed plan and explicit
  approval.
- Checkout is `validation_only`: it revalidates server-side price and fresh
  per-location inventory, records an idempotent attempt, and creates no Square
  order or payment.
- Merchandising publication writes only to Supabase CMS/versioning tables. It
  does not write to Square. Publication and rollback both require a digest-bound
  confirmation generated by an audit command.
- Never commit `.env`, `.env.local`, access tokens, database credentials, local
  Square caches, generated reports, or files under `tmp/`.
- Do not expose `/admin` or `/api/admin/*` publicly until a production identity
  provider is selected and verified.

## Read-only operational checks

Run from the repository root:

```bash
npm ci
npx prisma migrate status
npm run audit:constraints
npm run sync:square:postgres:readonly -- --status
npm run sync:square:postgres:readonly -- --checkout-readiness
```

The Square commands require the ignored local environment values documented in
`docs/environments.md`, including the Production read-only kill switch. The
readiness command exits nonzero while the reviewed content remains a DRAFT or
the current PUBLISHED payload is intentionally empty; inspect its per-location
results rather than interpreting that state as a sync failure.

## Safe merchandising workflow

Audit commands do not mutate data:

```bash
npm run prepare:merchandising:no-shipping
npm run publish:merchandising
npm run rollback:merchandising
```

Each apply command requires the exact confirmation printed by its corresponding
audit. Do not publish version 4 merely to begin development; local storefront
work and tests can continue while it remains a DRAFT. See
`docs/square-integration.md` for the full commands and invariants.
